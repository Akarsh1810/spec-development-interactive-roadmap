01

Discover the problem and define scope

Agree on what must change before touching code.

SDLC: PlanningOwner: Product + EngineeringOutput: accepted requirements
⌄

Actions

Example requirement

As a user, I can import a CSV or spreadsheet so I can view its records in the app.
  • Valid file: show row count and preview.
  • Invalid format: explain the reason without crashing.
  • Large file: enforce a documented size limit.
  • Acceptance: automated tests cover valid, empty, malformed, and oversized files.
Be careful: vague requirements create rework. Do not promise a feature until permissions, failure behavior, data retention, and acceptance criteria are understood.
02

Explore, specify, and design

Turn the requirement into a reviewable plan.

SDLC: Analysis & designOutput: spec + design + tasks
⌄

OpenSpec workflow

If OpenSpec is installed and integrated with your coding agent, use its supported commands to explore the change, draft a proposal, review the spec/design/tasks, then apply the work. Exact slash-command names depend on the agent integration and installed version.

Install / initialize (where supported)
npm install -g @fission-ai/openspec@latest
openspec init
Example agent actions (not shell commands)
/opsx:explore [feature]
/opsx:propose
Review proposal, specs, design, and tasks before applying.

Design review checklist

Review before implementation: specs and design documents are proposals, not proof of correctness. A human should check assumptions, data handling, dependencies, and scope before code generation.
03

Prepare the development environment

Verify the project’s toolchain before changing files.

SDLC: Environment setupOutput: reproducible local setup
⌄

VS Code — backend / web

Open the repository folder, inspect README and package manifests, install only project-required extensions (language support, formatter, linter, Git, test runner), then use the integrated terminal.

Baseline checks (run only for your stack)
git status --short
git branch --show-current
go version          # Go projects
node --version      # Node projects
npm --version       # Node projects
python3 --version   # Python projects

Run only the checks relevant to the repository. Use its pinned version files and package manager.

Android Studio — Android app

Install Android Studio and the project-required Android SDK. Open the project root (usually the folder containing settings.gradle or settings.gradle.kts), wait for Gradle sync, and resolve SDK/JDK versions from project documentation.

Device and build checks
adb version
adb devices
./gradlew tasks
./gradlew test

On Windows use gradlew.bat. A connected emulator/device should appear in adb devices.

Be careful: never commit API keys, keystores, signing passwords, production credentials, or local environment files. Do not upgrade SDKs, Gradle, JDK, or dependencies casually; verify compatibility first.

Implement in small, reviewable changes

Build one task at a time and keep the diff understandable.

Implementation loop

Git commands

Safe starting checks
git status
git switch -c feature/short-description
git diff --check
git diff
Review before commit
git status --short
git diff --check
git diff --stat
git diff
AI-generated code: treat it as an untrusted contribution. Check licensing and dependency changes, injection risks, authorization checks, concurrency, resource cleanup, and whether tests actually assert the requirement.
05

Test behavior and quality

Prove the acceptance criteria with repeatable checks.

SDLC: TestingOutput: test evidence
⌄

Backend / web examples

Go
gofmt -w .
go test ./...
go test -race ./...
go vet ./...
Node.js (if scripts exist)
npm ci
npm run lint
npm test
npm run build

Use scripts declared by the repository. Do not run commands blindly if the project uses another package manager.

Android examples

Gradle checks
./gradlew test
./gradlew lint
./gradlew assembleDebug

Also test on emulator/device: permission denial, rotation, offline state, process recreation, accessibility, and supported Android versions where relevant.

Required test layers

Do not: remove a failing test just to get a green build, use real customer data in tests, or treat “it compiles” as “it works.” Record the command and result for each important check.
06

Security, data, and performance review

Inspect the risks that ordinary happy-path tests miss.

SDLC: VerificationOutput: reviewed risk list
⌄

Security checklist

Data and reliability checklist

High-risk changes: authentication, payments, personal data, database migrations, file uploads, cryptography, permissions, and production infrastructure require explicit peer review and a rollback plan. Never test destructive operations against production.
07

Review, CI, staging, and release

Release only when the change is traceable and reversible.

SDLC: DeploymentOutput: approved release
⌄

Pull request / CI gate

Android release notes

  • Confirm application ID, version code/name, target SDK, and release variant.
  • Use secure signing configuration; never commit signing keys or passwords.
  • Test the signed release build, not only the debug build.
  • Follow Play Console policy and staged rollout requirements if publishing.
Pre-release status checks
git status --short
git diff --check
git log -5 --oneline
Release gate: all critical tests pass, approvals are recorded, migrations and rollback are ready, monitoring is in place, and the team knows who owns the release.
08

Monitor, document, and close the loop

Confirm production health and preserve what was learned.

SDLC: Operations & maintenanceOutput: stable service + updated docs
⌄

After deployment

Close-out evidence

  • Link to merged pull request and build.
  • Test commands and outcomes.
  • Migration / rollout / rollback details.
  • Known limitations and follow-up issues.
  • Archive or mark the spec/change complete using the workflow supported by your installed OpenSpec integration.
Keep the feedback loop: production incidents and user feedback should create new requirements and regression tests, not just one-off fixes.
